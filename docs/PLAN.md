# FF14 潜艇收益统计工具 — 技术方案

> 状态：v0.4 待确认。本文档用于评审，确认后作为实现依据。
> 代号：`FFXIVSubLedger`（可改），工作目录 `E:/dev/qianting`。

## 1. 目标与范围

做一个 Windows 桌面应用，解决「潜艇收艇后手动记账太麻烦」的问题：

1. 玩家收完艇，截取**背包区域**的图（或从剪贴板取图）。
2. 程序自动定位网格、切分格子，**识别每个格子里的道具图标**，得到道具与数量。
3. 按**游戏内固定的商店卖店价**算出本次收益。
4. 归档到对应角色/部队。
5. 提供统计页：日均、月均、年均、趋势、道具占比等。

支持多角色：事先配置好角色清单。只有一个角色时自动归属；有多个角色时，识别完成后弹出选择框，由玩家决定本次收益归到哪个角色。

**明确不做**：

- 不查市场价、不联网取价、不做价格缓存。潜艇产出全部卖店，价格由游戏内固定值决定。
- 不注入游戏进程、不读写游戏内存、不解析游戏 DAT 文件、不自动操作游戏。

因此本软件**可以完全离线运行**，除软件自身更新外不产生任何网络请求。

## 2. 调研结论（事实依据）

| 结论 | 依据 |
| --- | --- |
| 识别对象是**图标**，不是文字 | 产品设定：截图只截背包区域的纯图标 |
| 图标是游戏固定素材，跨服跨语言一致 | 国服与国际服共用同一套 UI 图标资源，因此不需要区分客户端 |
| 图标资源可批量获取 | 实测 `xivapi.com/i/026000/026001.png` 返回真实 PNG；`beta.xivapi.com` 的 asset 接口同样可用 |
| 卖店价是固定数值，可离线内置 | `thewakingsands/ffxiv-datamining-cn` 的 `Item.csv` 含 ItemId ↔ 名称 ↔ 卖店价 ↔ IconId |
| 潜艇掉落物种类有限 | 灰机 wiki「部队潜水艇/掉落」为可枚举的固定表；收益主体是 8 种沉船首饰 |
| 截图里**带数量数字** | 产品设定：数量显示在格子右下角（数量为 1 时游戏通常不显示） |
| **截图区域与边界不固定** | 产品设定：人工截图无法精准对齐，每次框选范围都会变 |

**关键判断**：

- 识别对象是图标而非文字，候选集是**封闭的小集合**（几十种），匹配只需在集合内取最相似，不需要开放域识别，也不受客户端语言与字体渲染影响。
- 计价链路退化成一次查表，无网络依赖。
- **截图边界不可信**，因此网格必须从图像内容中自行检测（周期性结构），而不能按截图边框等分。这是本方案最需要打磨的一环。

## 3. 技术栈（沿用两个既有项目）

与 `FFXIVConfigManager`、`XIVLauncherProxy` 保持一致，复用你已有的构建、发布、自动更新、本地化基建：

- C# / .NET 10 LTS
- Avalonia UI 12 + CommunityToolkit.Mvvm（MVVM）
- **OpenCvSharp4**（.NET 的 OpenCV 封装）用于网格检测、图标匹配、数字识别
- 模块化单体，分层：`Domain` / `Application` / `Infrastructure` / `Platform.Windows` / `Desktop`
- xUnit 自动化测试
- 界面文案暂用硬编码简体中文；`.resx` 本地化体系（参考项目的 `{l10n:Tr}`）暂未引入，需要多语言时再补
- 发布：Windows 自包含单文件，GitHub Release + SHA-256 校验 + 自动更新
- 许可证：GPL-3.0-only（与参考项目一致）

**为什么不选 Tauri / Electron**：两个参考项目都是 C# + Avalonia，工具链、发布流程、自动更新逻辑可以直接复用；图标匹配依赖 OpenCV，.NET 侧的 OpenCvSharp4 集成成熟；单文件便携分发更省事。

## 4. 系统架构

```text
FFXIVSubLedger.Domain          角色、部队、收益记录、道具、卖店价等领域模型与规则
FFXIVSubLedger.Application     识别编排、记账、统计等用例与接口

```

约束沿用参考项目：`Domain` 不依赖 UI、系统、数据库；`UI` 不直接操作文件，全部经 `Application` 用例编排。

**界面框架**：窗口骨架照搬 `FFXIVConfigManager`——`App.axaml` 只保留 `FluentTheme` 与 `ViewLocator`，样式定义在 `Window.Styles` 或各视图内部；左侧 220px 侧栏 + 右侧「页头 / 内容 / 底部说明」；卡片与分隔线用半透明叠加色（`#0A808080` / `#40808080` / `#0E808080`），文字层级靠 `Opacity` 表达，主题跟随系统。新增页面按同一套写，不要另起一套颜色。

## 5. 核心流程

```text
背包区域截图 / 剪贴板 / 拖入图片
        │
        ▼
  网格自动检测（从图像内容求格子周期与相位，不依赖截图边界）
        │
        ▼
  切分结果预览（原图叠加格子框，可手动微调 / 手动标一格兜底）
        │
        ▼
  逐格处理：空格子跳过 → 图标归一化 → 与图标库匹配
        │
        ▼
  数量识别（格子右下角数字）
        │
        ▼
  识别结果确认界面（可改数量、可换道具、可删除、低置信度高亮）
        │
        ├──► 多角色？──► 弹出角色选择（记住上次）
        ▼
  查表取卖店价 → 数量 × 单价 = 本次收益
        │
        ▼
  写入收益记录（SQLite）──► 统计页刷新
```

**识别结果必须经人工确认后才落库**。这是保证数据质量的关键设计，不是可选步骤。

## 6. 关键模块设计

### 6.1 截图获取

三条入口，都做：

1. **全局热键**：按快捷键后框选屏幕区域截图（推荐主用）。
2. **剪贴板**：点「读取剪贴板」，取当前剪贴板里的图片。
3. **拖入文件**：把已保存的截图拖进窗口。

由于截图边界不可信，**截图入口不做任何对齐假设**，一切交给后续的网格检测。

### 6.2 网格检测与切分（关键环节）

背包是规则网格，但框选范围随机，所以不能按边框等分。

**正方形先验（实测确立，优先使用）**：

格子是正方形，而行方向的可见行数通常很少（样本只有 2 行），导致行向自相关不可靠——多尺度测试中行向仅 3/7 档命中，列向 7/7 命中。因此：**以列方向检出的周期作为格子边长，行方向沿用同一周期，只单独搜索相位**。这同时把行向的搜索从二维降为一维。若遇到非等比缩放，允许手动覆盖行向周期。

**检测方法**（按优先级组合，取置信度最高者）：

1. **投影 + 周期分析**：对区域做边缘/梯度增强，沿水平与垂直方向求投影曲线，用自相关或 FFT 找主周期，得到格子边长与网格相位。只要图中有 2 个以上完整格子，就能推算整个网格。
2. **轮廓/直线检测**：背包格子有可见边框，用边缘检测 + 霍夫直线找横竖网格线，聚类求等距序列。
3. **格子模板匹配**：以游戏内裁出的标准格子为模板做多尺度滑动匹配，取响应峰值点作为格子中心。

**关键约束**：

- **只处理完整格子**：被截图边缘切掉的残缺格子直接丢弃，不参与识别。
- **空格子过滤**：格子内像素方差过低（纯背景）判定为空位，跳过，不进入匹配。
- **多尺度**：格子边长随 UI 缩放变化，检测出的边长用于自适应缩放，不写死像素值。

**兜底与人工干预**：

- 切分结果以**原图叠加格子框**的形式预览，用户可直接看出对齐是否正确。
- 自动检测失败或偏差时，允许用户**手动拖一个参考格**，程序据此推算整个网格。
- 允许手动整体平移/微调网格。

### 6.3 图标匹配与数量识别

**图标匹配**：

- 预处理：裁掉格位边框与右下角数量区域，只取图标主体；缩放到统一尺寸；转灰度并做颜色归一化。
- 主算法：**归一化互相关（NCC）/ 均方误差（MSE）**。图标是固定素材，对齐缩放后像素级差异很小。
- 辅助：HSV 直方图、dHash 做快速预筛，减少全量比对开销。
- 抗滤镜：ReShade/GShade 会改变颜色，因此**以灰度结构特征为主、颜色为辅**，并在匹配前做颜色归一化。
- 输出 top-N 候选与置信度，供确认界面使用。

**数量识别**：

- 数量显示在格子右下角（数量为 1 时游戏通常不显示数字）。
- 数字字体固定，用模板匹配（自己从游戏截图切一套 0-9 模板）即可，成本低、准确率高。
- 读不到数字时默认按 1 处理，由用户在确认界面修正。

**同图标多道具的处理**：

- FF14 中同一个图标可能被多个道具共用，且这种情况有多有少。
- 策略：**按需展开候选**。若某图标在掉落表中只对应一个道具，直接确定；若对应多个，确认界面把候选列出来供选择，默认选中卖店价最高的那个。
- 记录用户的历史选择，下次遇到同一图标时把上次选中的排在前面。

### 6.4 图标库与卖店价（离线内置）

- 内置一份**潜艇掉落候选表**：图标文件 + 道具名 + 卖店价。
- 图标从 XIVAPI 按 IconId 批量下载（约几十张 PNG），随程序分发，无需运行时联网。
- 道具名与卖店价来自 `ffxiv-datamining-cn` 的 `Item.csv`，以可读 JSON 形式随程序分发，用户可查看、可手工补充。
- 提供「更新掉落数据」入口：可拉取最新数据文件（唯一可选联网点），也可完全离线手动替换。
- 版本变化导致新增掉落时，未在表中的图标在确认界面标为「未知」，允许手工录入名称与卖店价并保存到本地补充表。

### 6.5 多角色 / 多部队管理

- 实体：`角色`（角色名 + 服务器）与 `部队`（FC）。潜艇归属部队，收益最终归到角色。
- 单角色：识别完成后直接归属，不打断。
- 多角色：识别完成后弹出选择框，默认选中上次选择；可在设置中指定默认角色。
- 角色可启用/停用，停用的不出现在选择框（类似参考项目的「只显示已标记角色」）。

### 6.6 数据存储

- 主存储：**SQLite**（统计要按日/月/年/角色/道具多维聚合，关系库比 JSON 更合适）。
- 可迁移性：提供 **JSON 备份导出/导入**（合并或整体替换），与参考项目的开放格式习惯一致。
- 备份内容：角色/部队配置、收益记录、本地补充的掉落数据。

### 6.7 统计与可视化

- 指标卡：历史总收益、**日均**、**月均**、**年均**、运营天数、收艇次数。
- 口径需明确：日均 = 总收益 ÷ 运营天数（自然日跨度），是否剔除无记录日作为可选项。
- 趋势图：每日折线、每月柱状。
- 维度对比：按角色 / 按部队。
- 占比：按道具（首饰 vs 材料）饼图。
- 消耗项（青磷水、修理材料）如果玩家关心，可作为可选统计，不影响收益主口径。

图表用 Avalonia 兼容的图表库（如 LiveCharts2 或 ScottPlot），或自绘轻量图表。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **截图边界不齐、格子被切残** | 切分错位 | 从图像内容检测网格周期与相位；只处理完整格子；切分结果可视化预览 + 手动标参考格兜底 |
| **同图标对应多个道具** | 无法仅凭图标区分 | 按需展开候选供选择，默认取卖店价最高者，并记忆历史选择 |
| 空格子被误判为道具 | 记入不存在的收益 | 空格子方差过滤 + 人工确认 |
| UI 缩放/分辨率变化 | 格子边长变化 | 边长动态检测，多尺度匹配，不写死像素值 |
| 滤镜（GShade/ReShade）改变颜色 | 匹配分数下降 | 以灰度结构特征为主 + 匹配前颜色归一化 |
| 数量数字识别失败 | 数量错误 | 数字模板匹配 + 默认按 1 + 人工确认兜底 |
| 掉落表随版本过期 | 新图标识别不到 | 数据文件可替换 + 未知图标手工录入 |

## 10. 样本截图实测参数

对样本 `Image_2026-10-14_18-35-15_elzp13tk.qab.png` 的实测结果（分析工具 `tools/analyze_grid.py`，叠加图 `tools/out/grid_grid.png`）：

| 项目 | 实测值 |
| --- | --- |
| 图像尺寸 | 371 × 177 px（PNG） |
| 格子边长 | **69 × 69 px**（正方形） |
| 可见布局 | 5 列 × 2 行 |
| 网格起点 | (26, 29) |
| 自相关相关度 | 列方向 0.435 / 行方向 0.234 |
| 空格子灰度 | 均值 60、标准差 10 |
| 有图标格子灰度 | 均值 78–132、标准差 44–71 |
| 数量数字 | 格子右下角，白色带黑描边，高约 20 px |

**由此确立的两条实现判据**：

1. **空格子判据**：格位灰度**标准差 < 15** 即判定为空位。实测空格子标准差 10，有图标格子 44–71，两者分离度极大，判据可靠。
2. **网格检测可行**：自相关法能稳定检出 69 px 周期。但行方向相关度仅 0.234，说明单靠投影容易被图标内容干扰，需要配合边框暗线做相位细化。

**第 3 条判据（真实数据才发现）**：铺网格线时，右侧必须留出「贴着最后一格边缘裁」的余量。样本的竖线是 `26, 95, 164, 233, 302, 371`——**最后一条正好等于图像宽度 371**。最初用 `position < length` 铺线，把这条边界丢掉，5 列被算成 4 列，最右一列道具（绿宝石 ×25）整个丢失。合成测试全绿，只有真实样本抓到了这个 bug，因此 `GridDetectorTests` 里补了两条合成回归 + `RealBagSampleTests` 用真实样本锁死（样本存为 `Recognition/Samples/bag-371x177.pgm`，无压缩，测试不依赖图像库）。

反面同样要防：右侧留白不能当成一列。但留白宽度接近一整格时，几何上和「一个空背包格」无法区分，此时**宁可多算一列空格子，也不能少算一列真格子**——空格子不参与计价，代价只是显示上多一格。

**多尺度鲁棒性测试**（`tools/test_scale.py`，用图像缩放模拟 UI 倍率变化）：

| 模拟倍率 | 期望格边长 | 列向检出 | 行向检出 |
| --- | --- | --- | --- |
| 0.50x | 34 | **35** | 30 |
| 0.75x | 52 | **52** | 46 |
| 1.00x | 69 | **69** | **69** |
| 1.25x | 86 | **86** | **86** |
| 1.50x | 104 | **103** | 93 |
| 2.00x | 138 | **138** | 124 |
| 3.00x | 207 | **207** | **207** |

结论：**列向周期检测 7/7 命中**，尺度鲁棒；**行向仅 3/7 命中**，原因是可见行数太少（样本仅 2 行），自相关信号弱（相关度 0.21–0.25，列向 0.29–0.43）。这直接确立了上面的「正方形先验」设计。

**必须注意**：以上数值只对**这张样本的 UI 缩放**成立。格子边长随游戏 UI 缩放变化，实现中必须动态检测，不能写死 69 px。另外，当格子缩小到 40 px 以下时（如 0.5x 档），数字只有约 10 px 高，数量识别余量不足，需依赖人工输入兜底。
