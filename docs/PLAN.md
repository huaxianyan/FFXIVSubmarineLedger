# FF14 潜艇收益统计工具 — 技术方案

> 状态：v0.5。v0.4 及以前按「截图 → 网格检测 → 图标匹配」设计；2026-10-27 需求变更后改为「截图游戏日志 → 识别文本 → 物名匹配」，日语优先。
> 项目名：`FFXIVSubmarineLedger`（仓库、程序集、可执行文件、数据目录同名），工作目录 `E:/Dev/FFXIVSubmarineLedger`。

## 0. 需求变更（v0.5）

| 项目 | v0.4 | v0.5 |
| --- | --- | --- |
| 识别对象 | 背包区域的**道具图标** | 游戏日志窗口里的**入手文本行** |
| 识别难点 | 网格从图像内容自行推算 | 日文文本识别 + 词表约束纠错 |
| 语言 | 与语言无关（图标跨语言一致） | **按语言分**，日语先行 |
| 数量来源 | 格子右下角的数字 | 日志行里的入手数 |
| 人工兜底的形态 | 手动标参考格、微调网格 | 逐行确认、改数量、删掉误收的行 |

因此 v0.4 的网格检测与图标匹配整层退役，实测记录保留在附录 A。截图入口、角色/部队、SQLite、界面框架继续用。

初版之后要做的「直接读取游戏内文本」见第 12 节，本版不实现，但分层要提前留出位置。

## 1. 目标与范围

做一个 Windows 桌面应用，解决「潜艇收艇后手动记账太麻烦」：

1. 玩家收完艇，截取**游戏日志窗口**的图（或从剪贴板取图）。
2. 程序定位文本行，识别日文，从「入手」类日志行里取出**物名与数量**。
3. 按游戏内固定的卖店价算出本次收益。
4. 归档到对应角色/部队。
5. 提供统计页：日均、月均、年均、趋势、道具占比。

多角色：事先配好角色清单。只有一个角色时自动归属；有多个时识别完弹选择框。

**明确不做**：

- 不查市场价、不联网取价、不做价格缓存。潜艇产出全部卖店，价格由游戏内固定值决定。
- **不注入游戏进程、不自动操作游戏、不解析游戏 DAT 文件。**
- **允许读取聊天框文本**（2026-10-27 用户明确要求）：通过 Sharlayan（MIT）做进程外内存读取，只读聊天框缓冲区，不写不改、不注入。这一步能彻底避开 OCR 误识（HQ 标记、形近字）。权限要求与游戏同级：游戏普通权限运行时本程序也能读（实测）；游戏自己提权时才需要跟着提权。
- 不读内存里的其它任何东西：不读角色属性、背包、地图、任务状态。
- 初版不做语言自动检测，语言由用户在设置里选定。

除软件自身更新外可以完全离线运行。

## 2. 调研结论

| 结论 | 依据 |
| --- | --- |
| 识别对象是**文本**，不是图标 | 2026-10-27 需求变更：日志里写着入手了什么、入手了几个 |
| 日志会显示入手名称与入手数 | 官方手册「アイテム入手：入手したアイテムの名称や入手数は、ログに表示されます」，并由真实样本核实（见下） |
| 物名是**封闭集合** | 潜艇掉落物种类有限（灰机 wiki「部队潜水艇/掉落」可枚举，主体是 8 种沉船首饰） |
| 物名与卖店价可离线内置 | `ffxiv-datamining-cn` 的 `Item.csv` 含 ItemId ↔ 名称 ↔ 卖店价；日文名需另找数据源（见 6.5） |
| 收录范围由截图决定 | 只识别截图内的连续日志行，不读全量历史日志 |

**关键判断**：识别退化成「在几十个候选物名里找最像的那一个」，不需要开放域识别。这决定了 OCR 不必完美——只要输出「足够接近的字符串」，由封闭词表做纠错与确认。这是选型时最重要的前提，直接决定 OCR 引擎可以选轻量的。

### 真实样本核实（2026-10-27，756 × 798 px）

两种来源都已实测：截图路径见下面的格式表；聊天框直读在游戏运行中一次读到 409 行真实聊天，格式差异记在 12 节。

样本为日服收艇后的日志窗口截图，含 4 艘潜水艦的入手记录，本地存于 `dev/samples/log-756x798.png`。它含角色名与潜水艦名，已进 `.gitignore`，**不入库**，只在本机当开发样本用。已确认的行格式：

| 日志行 | 实际形态 |
| --- | --- |
| 入手 | `[11:40] 角色名は ▶ 沈没船の高級首飾り×5を入手した。` |
| 入手（HQ） | `[11:41] 角色名は ▶ ゴールドインゴット◉×25を入手した。` |
| 探索完了 | `[11:40] 潜水艦「名称」の探索完了を確認しました。` |
| 修理 | `[11:40] ▶ シャーク級艦尾を修理しました。` |
| 出港 | `[11:40] 潜水艦「名称」が出港しました。` |

由此确定的解析事实：

1. **时间戳**是行首的 ASCII 方括号 `[HH:MM]`，不是全角括号。
2. **物名前有绿色三角标记**（物品链接标记），OCR 可能读成 `▶`/`►`/`▸` 或干脆读成空格，解析器必须容忍「有、变了、没有」三种情况。
3. **数量与物名同在一行、无空格分隔**，写作 `×N`，直接贴在物名后面（`沈没船の高級首飾り×5`）。这是最关键的切割点。
4. **HQ 物品在物名和 `×N` 之间多一个圆形标记** `◉`（`ゴールドインゴット◉×25`）。非 HQ 没有。**HQ 与 NQ 卖店价不同**（用户实测确认），所以这个标记必须一直带到计价环节，不能当噪声剥掉。
5. **同一物名会出现多行**（`エメラルド◉×29`、`エメラルド◉×27`）。收益按物名汇总，不能只认第一行。
6. 入手行与探索完了/修理/出港行**交错**在同一段时间戳里，必须按行模板筛，不能按「连续几行」切段。

版式实测（同一张图，工具 `tools/measure_log_lines.py`，纯标准库）：

| 项目 | 实测值 |
| --- | --- |
| 一屏可见行数 | 26 行（另有 3 条 2–4 px 的边缘亮边，定位时按行高归一滤掉了） |
| 行距 | 30–31 px（中位 30） |
| 单行字高（含描边） | 24–25 px |
| 文字左边距 | 13 px（各行一致） |
| 全图亮度分布 | p50 = 24、p90 = 180、p95 = 231 |
| 背景亮度跨度 | 8–180 |

**最后两行是本样本最重要的发现**：日志窗口没有底板，文字直接压在 3D 场景上，背景亮度跨越 8–180 的整段范围。因此**全局固定阈值二值化必然失败**，必须按行带做自适应阈值（局部双峰中点）。

## 3. 技术栈

沿用 `FFXIVConfigManager`、`XIVLauncherProxy` 的构建与发布基建：

- C# / .NET 10 LTS
- Avalonia UI 12 + CommunityToolkit.Mvvm（MVVM）
- SQLite（Microsoft.Data.Sqlite）
- xUnit
- 模块化单体：`Domain` / `Application` / `Infrastructure` / `Platform.Windows` / `Desktop`
- 界面文案暂用硬编码简体中文；`.resx` 本地化暂不引入
- 发布：`tools/publish.ps1` 打自包含目录包 → 去掉 PDB → 压缩为 `artifacts/FFXIVSubmarineLedger-<版本>.zip` → 生成同名 `.sha256`。只有 win-x64 一个包，所以文件名不带架构段。**不用单文件发布**：Tesseract 的本地库加载器（InteropDotNet）靠 `Assembly.Location` 拼路径，单文件打包后那是空值，构造引擎时直接抛空引用；实测已确认，不是猜测。自包含目录包比单文件大（约 54 MB），换来的是一钥直接能跑。
- 许可证：GPL-3.0-only

**图像与文本识别**：

- 图像预处理用纯 C# 实现（缩放、Otsu 二值化、行投影），不引入 OpenCvSharp4。v0.4 写的 OpenCvSharp 方案从未落地，实际代码一直是纯 C#，不要为已退役的路线补依赖。
- **OCR 已选定：Tesseract 5（NuGet `Tesseract` 5.2.0）+ 自带 `tessdata_fast` 日文模型**。模型 `jpn.traineddata`（2.4 MB）随程序放在 `Data/tessdata/`，不依赖系统装的 OCR 组件或语言包——本机就没有日文语言包，而产品的目标本来就是「软件自己解决 OCR」。
- 放弃 `Windows.Media.Ocr`：它需要用户自己装日文语言包，不满足上面那条。
- `tessdata_best`（14 MB）是现成的升级旋钮：实测只多认对一个「首」字，代价是耗时翻倍且在词间插空格，目前不用。
- 引擎接口仍是 `ITextRecognizer` 形态（实现在 `Infrastructure/Recognition/TesseractLineReader`），换引擎不惊动解析、计价、存储。

OCR 实现放在通用 `Infrastructure`（Tesseract 跨平台），`Domain`/`Application` 不接触它。

**构建环境**：`global.json` 钉 `10.0.400` 且 `rollForward` 为 `latestPatch`，即只接受 10.0.4xx。本机已装 10.0.403（`winget install Microsoft.DotNet.SDK.10`，机级装到 `C:\Program Files\dotnet`），`dotnet build` 与 `dotnet test` 均通过。不要为了绕 SDK 版本去改 `global.json` 或挪走它。

## 4. 分层与架构

```text
FFXIVSubmarineLedger.Domain          角色、部队、收益记录、道具、物名、卖店价等领域模型与规则
FFXIVSubmarineLedger.Application     识别编排、纠错、记账、统计等用例与接口
FFXIVSubmarineLedger.Infrastructure  SQLite、文本行定位、日志行解析、词表与纠错
FFXIVSubmarineLedger.Platform.Windows 剪贴板、全局热键、屏幕捕获、OCR
FFXIVSubmarineLedger.Desktop         Avalonia UI、MVVM、桌面交互
tests/                         Domain / Application / Integration 测试
```

约束沿用参考项目：`Domain` 不依赖 UI、系统、数据库；`UI` 不直接操作文件，全部经 `Application` 用例编排。

**界面框架**照搬 `FFXIVConfigManager`：`App.axaml` 只保留 `FluentTheme` 与 `ViewLocator`，样式定义在 `Window.Styles` 或各视图内部；左侧 220px 侧栏 + 右侧「页头 / 内容 / 底部说明」；卡片与分隔线用半透明叠加色（`#0A808080` / `#40808080` / `#0E808080`），文字层级靠 `Opacity`。新增页面按同一套写。

### 文本来源与文本解析分层

```text
文本来源：截图 + OCR（保底）/ 直接读聊天框（首选）/ （可选）剪贴板文本
              │
              ▼  IReadOnlyList<string>
LootScanner    解析行 → 对词表 → 算单价
```

两条来源都产出「一堆字符串」，后面完全共用：解析、纠错、计价、落库一行都不分叉。
这也是 2026-10-27 加聊天框直读时没有改动任何下游代码的原因。

## 5. 核心流程

```text
日志窗口截图 / 剪贴板 / 拖入图片
        │
        ▼
  文本行定位（行投影 + 行高归一，逐行给出边界）
        │
        ▼
  日文 OCR（整段读出，允许个别字错）
        │
        ▼
  日志行解析（按语言匹配行模板）→ 取出物名 + 数量
        │
        ▼
  物名词表比对与纠错（编辑距离 + 字形混淆表）→ ItemId
        │
        ▼
  确认界面（逐行：物名、数量可改；误收的行可删；低置信度标出来）
        │
        ├──► 多角色？──► 选择角色（记住上次）
        ▼
  查表取卖店价 → 数量 × 单价 = 本次收益
        │
        ▼
  写入收益记录（SQLite）──► 统计页刷新
```

**识别结果必须经人工确认后才落库**。这是数据质量的关键设计，不是可选步骤。原来靠「标参考格」兜底的地方，现在靠「逐行确认」兜底。

## 6. 关键模块设计

### 6.1 日志截图的获取

沿用已实现的四种入口：拖入文件、`Ctrl + V`、读剪贴板、选图片文件，外加待做的全局热键。

截取范围由用户决定，程序不做假设：把日志窗口里「本次收艇那几行」框进来即可，多框几行不影响（多余的行在确认界面删掉）。不要求对齐、不要求固定窗口尺寸。

### 6.2 文本行定位

日志是等行距的左对齐文本，和背包格子不一样，但「边界不可信」的约束同样存在。实测参数：行距 30–31 px、字高 24–25 px、左边距 13 px、一屏 26 行（见第 2 节）。

已实现：`TextLineLocator`。做三件事——行方向亮像素投影成带、按行高中位数滤掉明显偏短或偏长的带、逐行算墨迹左右边界。**不做左边界聚类过滤**：多留一行让人删，比少留一行让人重截便宜（旧图标路线吃过「宁可少算」的亏）。

真实样本实跑结果（`--dump-lines`）：26 行、左边界全为 13 px、行高 24–25 px、首行 top=9，与独立量测脚本 `tools/measure_log_lines.py` 一致。

后续仍要做的事：

1. **行分割**：灰度 → 方差/梯度行投影 → 阈值切出文本行带，带宽取中位数校正，避免某行有下划线或场景高光把带宽带偏。
2. **列对齐**：日志行有统一的左边界（时间戳）。按各行左边界做聚类，滤掉与主列相差过多的噪声行（例如误截进来的 UI 元素）。实测各行左边距完全一致，聚类门槛可以很严。
3. **行归属**：切出的行带统一 OCR，再交给行模板筛「入手」行；**不按「连续几行」切段**——入手行与探索完了/修理/出港行是交错的。
4. **多尺度**：日志字号随 UI 缩放变化，行高动态检测，不写死像素值。

行定位结果叠加回预览图（每行一个框），供人工核对是否把某行切半。

### 6.3 日文 OCR

已实现，链路是 `LinePreprocessor` → `TesseractLineReader`：

1. 裁行带，左右上下各留 2 px（裁掉假名的小勾与浊点就全错了）。
2. 双线性放大 3 倍。
3. **按行做 Otsu 二值化**，再用「严格大于阈值」判文字——阈值是背景类的最高灰度，用 `>=` 会把背景一并算进文字，整行变黑（写测试时踩到过）。
4. 反相成白底黑字后交给 Tesseract，`PageSegMode.SingleLine`、`EngineMode.LstmOnly`。

日志窗口没有底板，文字压在 3D 场景上，实测背景亮度跳 8–180，所以全局固定阈值必然失败，Otsu 必须每行单独算。滤镜（GShade/ReShade）只改对比度与色偏，预处理只依赖亮度结构，不受影响。

**真实样本实测（26 行，含 14 条入手行）**：

| 项目 | 结果 |
| --- | --- |
| 行级 | 26/26 行都读出了内容 |
| 物名 | 13/14 完全正确；错的那条是「高級首飾り」变「高級括飾り」，编辑距离 1 |
| 数量 | 14/14 数字全对 |
| 耗时 | 26 行约 3 s（含引擎初始化与图像管线，单行约 30 ms） |

**固定误读（要靠归一与词表收拾，不是模型问题）**：

- `▶` 读成 `p` 或 `b`；
- `×` 读成 `X`、`x`、`※`、`メ`，甚至直接吞掉（`エメラルド29`）；
- HQ 标记 `◉` 读成 `6ぐ`、`で`、`ゅ`。

这些字符恰好都不在物名里，因此「先去掉噪声字符再匹配词表」不会被它们干扰。汇总见 6.5。

### 6.4 日志行解析（按语言）

每种语言一个 `IChatLogParser` 实现：

```text
IChatLogParser.TryParse(LogLine line, out LootEntry entry)
```

- 日语实现 `JapaneseChatLogParser` 先行；中文、英文按需补。新增语言 = 加一个解析器 + 一份物名表，UI、存储、统计不动。
- 只认「入手」类行。任务奖励、副本掉落、市场购买等同样是入手消息，靠「只取截图内的连续行 + 人工确认」隔离，不靠语义猜测。
- 语言解析器不依赖 OCR 的具体输出形态，只吃字符串。

**行模板（按第 2 节样本核实的真实格式）**：

```text
入手    ^\[(?<time>\d{1,2}:\d{2})\]\s*(?<actor>.+?)は\s*[▶►▸]?\s*(?<item>.+?)[◉]?\s*[×x]\s*(?<qty>\d+)\s*を入手した。?$
```

解析要点：

- 三角标记 `▶` 可能被 OCR 读成别的符号或丢失，因此写成可选。
- HQ 标记 `◉` 紧贴在物名与 `×N` 之间，**从物名里剥离但要保留为标志位**（`IsHighQuality`）。它直接决定单价（HQ 比 NQ 贵一成，见 6.5），丢了就是算错钱。
- 同一 `ItemId` 的 HQ 与 NQ 在落库时**不合并**（单价不同，合并后无法反推）。
- 数量分隔符同时接受全角 `×` 与 OCR 常见的 `x`。
- `actor` 是「角色名は」里的角色名，用于校验这笔记录归属，不作为识别目标。
- 不匹配的行（修理、出港、交叉频道发言）直接丢，不报错。
- **艇名是收益的归属凭据**：`潜水艦「X」の探索完了を確認しました。` 这一行出现在它那批收益行**之后**，所以归属要倒着算——先把入手行攒着，遇到「探索完了」就整批结算给那艘艇。
- **归属必须在整段有序缓冲上算**。只拿「这一轮新出现的几行」去解析，往往拿不到后面那行「探索完了」，归属就会从错误的上文里算出来。实测踩过：`沈没船の高級耳飾り×5` 这种行文本会在两艘艇下各出现一次，切片解析把 Cranberry 的那笔算成了 Blackberry（总额不变，分艇错 15 万）。
- 因此监听路径的流程是：整段扫描 → 得到完整且带归属的条目表 → 用「艇名 + 原始行」作键去重 → 只把没落过的落成行。还没等到「探索完了」的条目不结算，等下一轮。

**仍然未知、需要再取样本的点**（不阻塞当前实现）：

- 长物名在窄日志窗口里**换行**时的行形态（样本里没有触发）；
- 关闭时间戳显示（`/chatlog time`）后的行首形态；
- 中文与英文客户端的行模板（M3 只做日语）；
- 不同 UI 缩放下的字高与可识读性下限。

上述未知项都不影响行模板的主体结构，但换行那一条一旦出现，会让「一行一条入手」的前提失效，因此确认界面必须允许手动补行。

#### 金额与容量

- **金额一律 `long`**。每天收四艇约 360 万 Gil，一年 3.6 亿；`int` 上限 21.4 亿，六年不到就会溢出，统计页会直接抛 `OverflowException`。SQLite 的 `INTEGER` 本来就是 64 位，只有 C# 这层是瓶颈。写这条时用 30 亿的测试数据复现过。
- **主显示是概数，副行才是精确值**：一眼要看出量级，所以大字写「173 万 Gil」，下面小字写 `1,730,883 Gil` 供核对。单位词走 i18n 的 `money.tenThousand` / `money.hundredMillion`。
- **概数最多一位小数**（`141.8 万`、`3.6 亿`），看量级用；小数位截断，不四舍五入。
- **换单位的门槛正好是一亿**，没满就还是「万」（`99,999,999` → `9999 万`）。整数截断，不四舍五入，所以不会出现「10000 万」这种既不是一万万也不是一亿的写法。
- 一万以下概数就等于精确值，不显示副行。
- **铺开的位置**：统计页四张指标卡、三种占比行（角色/艇/道具）、已入账记录行、趋势图纵轴、记账页的合计与存盘提示。CSV 与备份里仍是原始整数（那是数据，不是展示）。
- **容量实测量级**：每天 4 笔记录 / 13 条明细的节奏下，一年 **约 1.2 MB**（1460 笔、5840 条明细，约 216 B/明细、864 B/记录），十年约 11 MB。`VACUUM` 后一年 1.15 MB、十年 11 MB。数据库放在 `%LocalAppData%`，这个量级几十年都不需要担心。

### 更新检查与代理

- **只查版本号**：`GET https://api.github.com/repos/huaxianyan/FFXIVSubmarineLedger/releases/latest`，比对 `tag_name` 与当前版本。不下载、不安装、不上传任何东西。
- 启动时查一次（可在设置页关掉），设置页也能手动查；两处走同一个 `UpdateService`，共享上次结果。
- **语义边界**：仓库还没发过正式版时 GitHub 回 404，这按「已是最新」处理，不算失败。失败分三类并分别出文案：连不上（网络/代理/超时）、HTTP 非 2xx、响应读不懂。
- **代理**：三种模式——跟随系统 / 不使用 / 自定义。自定义时**协议、地址、端口分开填**（协议从 HTTP / SOCKS5 / SOCKS4 / SOCKS4a 里选），用户不用自己拼 `http://主机:端口`。换协议时端口自动补成该协议的默认值（HTTP 8080、SOCKS 1080），用户填过的不覆盖。
- **协议只列 `SocketsHttpHandler` 认的四种**：http / socks4 / socks4a / socks5。写 `https://` 能存进设置、要到发请求时才抛 `NotSupportedException`，所以界面上干脆不提供，`ProxySelectorTests` 钉住这个清单。
- 误填当场说清怎么改：把整条 URL 塞进地址栏、把端口写进地址里、带路径、端口越界，各有各的提示，而不是笼统一句「地址无效」。代理只用于更新检查，记账全程不联网。
- 旧版存的是一整串 `ProxyUrl`，读设置时自动拆成三个字段（`SqliteSettingsStore.MigrateLegacyProxyUrl`），否则老用户升级后代理会静默失效、只看到「检查更新失败」。
- 未使用 token：未认证每小时 60 次，手动点几下完全够；加 token 意味着要用户配密钥，不值。

### 显示语言（i18n）

界面与道具名支持多语言，**收集不受影响**：日志用哪种语言写，都照常按行模板解析。

- **语言资源**：`src/FFXIVSubmarineLedger.Application/Localization/language-*.json`，作为嵌入式资源随程序分发。每个文件自带 `language.tag`（如 `zh-Hans`、`ja`）与 `language.name`（如 `简体中文`、`日本語`）。
- **加一门语言不用改代码**：放一个 `language-<任意名>.json`，键与现有语言对齐即可。设置页的语言下拉直接由 `Loc.Available` 生成，键集合由测试 `LocalizationTests.EveryLanguageHasTheSameKeys` 守着。
- **文件名不能带点号分段的语言名**（如 `strings.ja.json`）：MSBuild 会把它当成附属程序集的文化，只生成卫星程序集，主程序里读不到。这个坑吃过一次，见项目档案。
- **缺键兜底**：当前语言 → 英语 → 默认语言（`zh-Hans`）→ 任意语言 → 键本身。
- **道具名跟着界面语言走**：`Data/items.json` 里每条是 `names: { "ja": ..., "zh-Hans": ... }`，用 `ItemId` 绑定。落库的物名只是规范写法，显示时按 `ItemId` 换成当前语言，所以改语言后历史记录也会跟着变。
- **金额单位统一写 `Gil`**（英文，前面留一个空格，如 `995,392 Gil`）。
- 界面文案走 `{loc:Tr key}` 标记扩展。每个绑定拿到自己的 `LocalizedText`（普通属性 + 弱引用登记），换语言时逐个通知，即时生效、不用重启。
  **不能绑到 `Loc` 的索引器**：Avalonia 12 的绑定引擎不会因 `PropertyChanged("Item[]")`（甚至属性名为空的全量通知）重新求值索引器路径，界面会一直显示旧语言——这个坑用无头测试钉住了，见下。
- 测试：`tests/FFXIVSubmarineLedger.Desktop.Tests`（xunit v3 + Avalonia.Headless）验证两件事：XAML 文案绑定能在换语言后刷新；视图里用到的每个键在每门语言里都存在。

## 6.5 物名词表与纠错

- 词表项：`ItemId`、日文名、**NQ 卖店价**、能否 HQ。价格与语言无关，物名按 locale 存（7 节 `ItemName`）。
- **HQ 价不存表，用公式算**：`HQ = ceil(NQ × 1.1)`。写成整数运算是 `(nq * 11 + 9) / 10`，不用浮点，不会 1 gil 偏差。
- `CanBeHq` 也是校验信号：不可 HQ 的物名后面如果 OCR 读出 `◉`，那一定是误识。
- 匹配策略：OCR 字符串去掉空白后，与词表逐条算编辑距离；允许的最大距离是 `min(2, 物名长度/4)`。距离相同按卖店价降序排，贵的排前面。
- **字形混淆表暂时没做**：实测下来日语模型在 3 倍放大 + 每行 Otsu 之后，错字都是单字替换，编辑距离已经够用；等真实样本里出现成体系的混淆（如 `ツ`/`シ`）再上。
- 命中唯一：直接确定。
- **命中多个必须显式标出来**：不能静默按第一个算钱。实测就有现成的例子——OCR 把「高級首飾り」读成「高級括飾り」，它到「高級首飾り」和「高級耳飾り」的编辑距离都是 1，默认值取贵的那个（34,500），但界面必须让人看见还有另一个候选。
- 全不命中：标「未知」，单价给 0，允许手打名称与卖店价，写进本地补充表。
- **HQ 标记可靠性有限**：`◉` 被 OCR 吞掉的概率不低（样本 14 条里有两条丢了），而 HQ 直接影响单价。因此 HQ 必须做成确认界面里可切换的开关，不能只靠识别。
- **同一物名多行**：样本里 `エメラルド◉×29` 与 `エメラルド◉×27` 是两行。识别时逐行处理，落库时按「`ItemId` + 品质」合并成一条 `LootItem`（数量相加）。

### 6.6 数量

- 数量在日志行里能读到就取读到的值。
- 读不到时默认 1，确认界面标出来让人改。
- 数量与物名分开核对：物名对、数量错是最常见的组合，确认界面里数量用独立输入框，不要藏在编辑对话框里。

### 6.7 确认界面与计价

已实现（`LootRowViewModel` + 收艇记账页）：

- 一行一条：勾选框（取消即不入账）、物名、OCR 原文小字（对照用）、**艇归属下拉**、候选下拉、数量 `NumericUpDown`、HQ 开关、单价与小计。
- **艇归属可人工改**：识别把相邻两艘艇的收益串起来时，在行内下拉里改回去。选项是本批出现过的艇 +「未标明艇」。
- **HQ 开关是硬需求**：识别本身靠不住（样本 14 条里丢了 2 个标记），必须能人工切。物名不能 HQ 时开关置灰，避免了「勾了但无效」。
- **候选下拉只在歧义时出现**，默认选卖店价最高的那个。不静默选、不藏起来。
- 词表外的物名给一个单价输入框，不填就不入账（行保持未勾选）。
- 合计与计入行数实时刷新，改数量、切 HQ、改候选、取消勾选都会重算。
- 「记入账」写到默认角色名下（没默认就取第一个）；没角色时提示去角色管理页建。写完清场并显示本次结果。

落库规则在 `Application/Records/LootRecordFactory`：合并键是「`ItemId` + 品质」，词表外物名用物名做键（否则不同未知物会因 `ItemId` 都是 0 被并成一条）。数量为 0 的行直接丢弃。

### 6.8 多角色 / 多部队

- 实体：`角色`（角色名 + 服务器）与 `部队`（FC）。潜艇归属部队，收益最终归到角色。
- **现状**：`部队` 只在模型、备份与 CSV 列里，界面还没有管理入口；现在记账一律归到角色，`free_company` 为空。做界面时要连潜艇归属一起改。
- 单角色：识别完成后直接归属，不打断。
- 多角色：识别完成后弹选择框，默认选中上次选择；设置里可指定默认角色。
- 角色可启用/停用，停用的不出现在选择框。

### 6.9 数据存储

- 主存储：**SQLite**（统计要按日/月/年/角色/道具多维聚合，关系库比 JSON 更合适）。
- **JSON 备份已实现**（设置页）：导出是明文本 JSON（`Version` + 导出时间 + 角色 + 部队 + 记录 + 明细），不用本程序也能看懂。
- **导入是整体替换**，不是合并：单个事务里删空子表再写入，中途失败就回滚，不留半份数据。导入前自动把当前数据导出到 `<数据目录>/backups/before-import-<时间>.json`，点错了还能退回来。
- 版本号不认识就拒绝，不猜着迁——猜版本是最容易把用户数据迁坏的做法。记录指向不存在的角色也拒绝。
- 未入备份：设置表（目前只有默认角色一类偏好）。补备份时要连 `settings` 一起读，并升 `Version`。
- **老库升级**：`Initialize()` 里除了建表，还会用 `pragma_table_info` 检查 `loot_records.submarine_id` 是否存在，缺了就 `ALTER TABLE ADD COLUMN`。不给用户「删库重建」这条路。

### 6.10 统计与可视化

已实现（口径全在 `Application/Records/LootStatistics`，界面只负责摆数）：

- 指标卡：历史总收益、日均、月均、年均。
- 口径：日均 = 总收益 ÷ 自然日跨度（最早到最晚，含首尾）；月均 = 总收益 ÷ 跨越的日历月数；年均 = 总收益 ÷ 跨越的日历年数。**不剔除没记录的日子**——收艇本来就是每天一次，空着的日子要么没运营要么漏记，剔除会把均值抬高。
- 道具占比：按物名汇总（HQ 与 NQ 合并计）后按收益降序，带占比条。
- 趋势图：每日或每月收益折线，自绘（`Desktop/Controls/TrendChart.cs`），不引图表库——只需要一条折线加三个刻度，图表库的坐标轴、主题与包体积成本不划算。中间无记录的日子补 0，否则折线会把「那天没收益」画成连续产出。
- 按角色占比：角色名、收艇次数、占比条、金额。
- 按艇占比：艇名、次数、占比条、金额；没有艇归属的收益单列为「未标明艇」。
- **筛选**：先选角色，再选艇。艇名只在角色范围内唯一，所以不选角色时艇下拉是禁用的——否则不同角色的同名艇会混在一起。
- **导出 CSV**：一行一条道具明细（日期 / 角色 / 部队 / 道具 / 数量 / 品质 / 单价 / 小计 / 备注），带 UTF-8 BOM——不带的话 Excel 会把中日文读成乱码。
- 已入账记录列表：日期、角色、明细、合计，可逐条删除。
- 统计只认已入库的记录，未确认的截图不计入。

待做：

- 维度对比还可按部队拆（模型里有 `FreeCompanyId`，但目前没有部队管理界面，写入时也不带）。
- 消耗项（青磷水、修理材料）如果玩家关心，作为可选统计，不影响收益主口径。

v0.4 的 `IconChoice`（同图标多道具的选择记忆）与图标字段随图标路线一起退役，其作用由 `ItemAlias` 承担。

艇是 2026-10-27 加的层级：角色 → 艇 → 记录。原因是聊天框直读能拿到「潜水艦「X」の探索完了」这一行，艇名就是天然的分组凭据。旧记录没有艇归属，`SubmarineId` 允许为空，统计时归入「未标明艇」。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 日志里混入非收艇的入手消息 | 收益虚高 | 行模板只认「入手」类行；确认界面逐行可删；不自动推断「这段日志属于哪次收艇」 |
| **日文物名 OCR 误识**（`カ`/`力`、`ー`/`一`、`ツ`/`シ`） | 物名匹配不上 | 封闭词表内编辑距离 + 字形混淆表降权；多候选时让人选并记住 |
| 数量不在同一行或被截断 | 数量错误 | 读不到默认 1 并标出；数量独立输入框 |
| UI 缩放、滤镜改变文字对比度 | 识别率下降 | 行高动态检测、按行带自适应二值化、放大后识别；不写死像素与阈值 |
| 日志窗口换行或被遮挡 | 行切半、内容缺失 | 行定位结果叠加预览；换行导致的断行无法自动拼回，确认界面允许手动补行 |
| **日志窗口没有底板**，字压在亮场景上 | 二值化失败、整行读不出 | 按行带自适应阈值（局部双峰中点）；实测背景亮度跳 8–180，不得使用全局阈值 |
| 同一物名多行 | 重复计入或漏计 | 逐行识别、按「`ItemId` + 品质」合并数量；确认界面显示合并前后的对应关系 |
| **HQ 与 NQ 卖店价不同** | 单价取错、整笔收益偏差 | HQ 标记全程保留（`IsHighQuality`）；单价按 `ceil(NQ × 1.1)` 算，不依赖逐物数据；`CanBeHq` 为假的物名读到 `◉` 按误识处理 |
| 词表随版本过期 | 新物名匹配不到 | 未命中标「未知」，允许手打并写进本地补充表 |
| **游戏提权后本程序读不到**（跨完整性级别被反篡改拦） | 功能用不了 | 报错说清「游戏以管理员运行时，本程序也要管理员运行」；OCR 路径与权限无关，可随时退回 |
| 读内存属于第三方工具行为，可能触及游戏用户协议 | 用户账号风险 | 不默认开启，由用户点「直接读聊天框」主动触发；文档里写明这一步在读内存 |
| 不同语言同名物或译名差异 | 认错道具 | 一律以 `ItemId` 唯一化，展示时才挂语言名 |
| 日语行模板猜错 | 解析全错，且难排查 | 先拿真实样本确认格式（第 11 节第 1 条），确认前不写解析器 |

## 12. 直接获取游戏内文本（已实现）

**目标**：不截图，直接从游戏里拿聊天文本，绕开 OCR 认错字的问题。

**实现**：`Platform.Windows/GameChat/SharlayanChatReader`，用 [Sharlayan](https://github.com/FFXIVAPP/sharlayan)（MIT）做进程外内存读取。参考了 [tataru-assistant](https://github.com/winw1010/tataru-assistant) 的做法（它也靠 Sharlayan 读游戏文本）。

关键实现细节（都是踩过之后写下的）：

- `ChatLogFirstRunReadsBacklog = true`，首次读取才会把聊天框里已有的行一起带出来；**连上之后不要额外 `GetChatLog()` 预热**，那会把缓冲白白消耗掉。
- 刚连上时读指针可能未就绪，要轮询（实测首个 500 ms 内才能拿到那 300 多行历史）；轮询封在 `ReadNewLines()` 里。
- 权限要求与游戏同级：反篡改机制会拦跨完整性级别的 `PROCESS_VM_READ`。实测游戏普通权限时本程序也普通权限就能读；只有游戏自己提权时才需要提权。
- 聊天内存里的行**没有**截图里的 `▶` 链接标记，且 `×` 更接近半角；解析器两种都吃。
- **HQ 在聊天框里写作物名后缀 `[HQ]`**（截图渲染才是 `◉`）。第一版没认这个后缀，`ルビー[HQ]` 被当成物名、匹配不上词表，价格归零且行未勾选，界面看着像「什么都没读到」。两种写法现在都认。
- 真存在「没有主语的入手行」（如「〜の景品として、…を入手しました。」），因此解析必须要求 `<角色名>は` 分隔符，不然会把非常山渠道的行计进收益。

**实测（游戏运行中）**：

- 一次读到 409 → 624 → 676 行真实聊天（随会话增长），认出的入手行与词表判定都正确。
- **读取器每次调用都把整段累计历史重给一遍**：同一进程里连读两次，两轮行数相同。所以调用方必须自己去重。
- 去重不能按「同一句话出现过几次」算：同名道具分属两艘艇时会被并成一条。实际做法是按「艇名 + 原始行」作键（`LootAccumulator`），还没等到归属的行先不结算。

**「先收完艇再开程序」能读到吗**：能，条件是没有被挤出去。游戏的聊天缓冲是**固定 1000 条的环形表**（Sharlayan 源码里明写 “fixed 1000-entry table”，回绕时按 1000 条回读），我们首读又开了 `ChatLogFirstRunReadsBacklog` 把缓冲历史整段带出来。因此只要收艇那几行之后没有刷出 1000 条新聊天，晚点开程序也能补读；被顶掉就退回截图识别。

**自动监听**：打开后每 3 秒轮询，出现新的入手行就追加到本次账。去重与追加都不清空用户已改过的行。命令本身写成同步方法，循环在后台跑——否则 `async` 命令执行期间按钮会被禁用，「停止监听」点不动（这是写完第一版才发现的）。

**保留的其它路线**（不实现，仅备查）：

| 路线 | 说明 | 代价 |
| --- | --- | --- |
| Dalamud 插件 | 官方支持的插件框架，插件内直接拿日志事件，经本地 IPC 交给应用 | 用户需装 XIVLauncher + Dalamud |
| 读 ACT 产出的日志文件 | ACT 插件已把日志落成文件，我们只解析文件 | 用户需装 ACT，依赖第三方格式 |
| 注入游戏进程 | 不采用 | 与第 1 节边界直接冲突 |

**边界（已按用户要求变更）**：允许读聊天框内存，但不注入、不写游戏内存、不读其它游戏状态。这条边界写在第 1 节，改动前先看那里。

## 附录 A：已退役的图标识别路线

v0.4 设计的是「截背包区域 → 网格检测 → 图标匹配」。路线退役的原因是识别对象变了，不是方案失败——实测中它工作得不错，记录留在这里，避免日后重复调研，也避免把它的结论误用到新路线上。

**当时的实测事实**（样本 371 × 177 px，分析工具曾是 `tools/analyze_grid.py`）：

| 项目 | 实测值 |
| --- | --- |
| 格子边长 | 69 × 69 px（正方形） |
| 可见布局 | 5 列 × 2 行 |
| 自相关相关度 | 列向 0.435 / 行向 0.234 |
| 空格子灰度 | 均值 60、标准差 10（判据：标准差 < 15 为空位） |
| 有图标格子灰度 | 均值 78–132、标准差 44–71 |
| 多尺度命中 | 列向 7/7、行向 3/7（行数太少，自相关弱） |

**留下的教训**（换路线后仍然成立）：

1. **合成测试盖不住真实约束**。曾经因为 `position < length` 把「网格线正好落在图像右边缘」那条线丢掉，5 列算成 4 列，整列道具丢失。只有真实样本抓到了。
2. **宁可多算，不可少算**。留白宽度接近一整格时，几何上无法与「一个空格」区分——宁多算一列空的，不少算一列真的。
3. 这条「真实样本回归 + 宁可多算」的做法应沿用到新路线：日志行宁可多读几行让人删，也不要把某一行切半漏掉。

**已删除**（2026-10-27，按新路线清理）：`GridDetector`、`GridOverlay`、`GridDetectionOptions`、`GridDetectionResult`、`IconExtractor`、`IconExtractionOptions`、`IconPatch`、`GrayImage`、`RgbImage`、`ScreenshotAnalyzer`，三个 `Recognition` 测试与 `Samples/bag-371x177.pgm`，以及 `tools/analyze_grid.py`、`tools/test_scale.py`。需要回顾时从 Git 历史取。灰度容器在写文本行定位时重新引入，不为旧路线提前留着。

### 图标

一枚金色浮雕潜艇纪念币。源图 `tools/icon-source.png`（1254×1254，纯黑背景），由 `tools/make_icon.py` 抠底、裁切、重采样后打包成图标。

- 产物：`Assets/app.ico`（16/24/32/48/64/128/256 七个尺寸，exe 与任务栏）、`Assets/app.png`（256，窗口标题栏）、`docs/icon.png`（README 顶部）、`docs/icon-sizes.png`（浅色与深色背景的尺寸对照）。
- 流程：按连通区域抠底 → 裁到不透明包围盒 → 补成正方形并留 2% 边距 → **修成正圆** → 面积平均重采样 → 按尺寸补对比 → 压高光。改图只需换掉 `tools/icon-source.png` 再跑一遍脚本。
- **币缘必须修成正圆**。源图边缘各角度半径在 471–492 之间摆动（暗边宽窄不一），缩到 19 px 就是一圈毛刺。做法：量出每个角度的边界半径取平均作正圆，圆内原本透明的地方用同方向「边界往里 2 px」的颜色补——那里是暗边，补出来还是一圈暗边。直接取最小半径做遮罩也能变圆，但会削掉 3.5% 的直径，且各角度切到的颜色不一致。
- **按尺寸补对比**（`CONTRAST`）。源图的浮雕是细纹理，高通后标准差只有 27/255，8×8 的整体明暗几乎是平的——缩小后必然被平均成一块平色。16 px 不补的话亮度标准差只有 25，补到 34。
- **高光要压**。币缘有一圈接近纯白的高光（`#FEFDE2`），缩到 19 px 成白斑。压缩后近白像素从 4.5% 降到 0。
- **先拉对比再压高光**，顺序反了等于白压：对比度曲线会把刚压到 0.87 的高光重新拉回 255（实测左缘回到 `#FEE377`）。
- **按连通区域抠底，不套圆形/椭圆遮罩**：这枚币边缘各角度半径在 472–490 之间，套圆形遮罩要么切掉一块、要么留一圈黑边。做法是从画布四边出发，把「亮度低于阈值且能连通到边界」的像素标成背景——币面凹陷处再暗也留着。
- **重采样必须走预乘 alpha**：不预乘的话，透明区域的黑色会渗进边缘，出现一圈脏边。
- **面积平均，不用双线性**：1254 → 16 是 78 倍缩小，双线性只采 4 个点，细节全丢还起锯齿；面积平均按覆盖度累加，等于自带低通。
- 先裁到包围盒再居中，边距按像素算。不裁会偏小且不居中，16 px 看得出来。
- 纯标准库，不装 Pillow。`--sheet` 出对照图、`--preview` 打 ASCII 预览（没有图像工具也能核对）。
- `ShellLayoutTests.WindowIconLoads` 断言窗口图标能加载：资源路径写错时 Avalonia 在建窗口时抛异常，表现成「双击没反应」。
